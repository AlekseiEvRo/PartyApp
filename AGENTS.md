# AGENTS.md

Party/event app: ASP.NET Core 9 minimal API (`src/`) + Svelte 5 SPA (`web/`). SQLite via EF Core, SignalR for realtime, JWT auth. User-facing strings and most code comments are Russian — keep new ones Russian.

## Layout

- `src/PartyApp.Domain` — entities, enums, abstractions; no infrastructure dependencies.
- `src/PartyApp.Infrastructure` — `AppDbContext`, EF configurations, migrations under `Persistence/Migrations`, wallet/file/QR services.
- `src/PartyApp.Api` — minimal API endpoints grouped by feature in `Modules/<Feature>/`, SignalR in `Hubs/`. `Program.cs` wires everything (DI, JWT, CORS, seeding).
- `web/` — Svelte 5 + Vite + TS PWA; Vite build output goes to `src/PartyApp.Api/wwwroot`.
- `tests/` — два xUnit проекта: `PartyApp.UnitTests` (реальная SQLite in-memory, NSubstitute, FluentAssertions) и `PartyApp.IntegrationTests` (`WebApplicationFactory<Program>`, реальные миграции в Temp-SQLite, SignalR). Детали и известные ограничения — `tests/README.md`. CI — `.github/workflows/ci.yml` (backend build+tests, frontend check+build).

## Commands

Backend (from repo root):

- `dotnet build PartyApp.sln`
- `dotnet test PartyApp.sln` (653 теста: unit + integration; `Program.cs` обязан оставаться доступным тестам через `public partial class Program`)
- `dotnet run --project src/PartyApp.Api` — http://localhost:5000, Swagger at `/swagger`; applies migrations and seeds event definitions on startup.
- New migration: `dotnet ef migrations add <Name> --project src/PartyApp.Infrastructure --startup-project src/PartyApp.Api -o Persistence/Migrations`. No design-time factory, so both projects are required; the `-o` is required to match the existing migrations and their namespaces. Never run `database update` — startup migrates.

Frontend (in `web/`):

- `npm run dev` — Vite on 5173, proxies `/api` and `/hubs` (incl. WebSocket) to `localhost:5000`.
- `npm run check` — svelte-check + tsc; the only frontend verification.
- `npm run build` — writes to `../src/PartyApp.Api/wwwroot` with `emptyOutDir: true`.

## Gotchas

- `src/PartyApp.Api/wwwroot` is generated output. Never edit it; edit `web/public/` (static files such as `signalr-test.html`, `push-sw.js`, icons) or `web/src`. `wwwroot/index.html` exists only after `npm run build`, so a fresh clone's API serves the SPA only post-build; during development use the Vite dev server. `npm run build` also rewrites/deletes some stale tracked assets under `wwwroot` and dirties git — don't commit those changes.
- `src/PartyApp.Api/App_Data/` (SQLite `party.db`, uploads, dictionary, `jwt.json`, `vapid.json`, `logs/`, `backups/`) is gitignored and absent from a fresh clone. `word_rush` requires `App_Data/russian.txt` (one word per line); without it every submitted word is rejected (`RussianDictionaryService`).
- No admin bootstrap anywhere: registration always creates `UserRole.Player` (`Admin = 10`, `SuperAdmin = 100`), поэтому первого админа заводят прямо в SQLite (`UPDATE Users SET Role = 10 WHERE Username = '...';`) и логинятся заново. Дальше роли, имена, блокировка, кик и сброс пароля доступны в админке (`PATCH /api/admin/players/{id}`, `POST .../kick`, `POST .../reset-password`). Смена роли/блокировка/кик/сброс пароля меняют `User.SecurityStamp`, поэтому старые токены сразу отклоняются (401) — нужен повторный вход.
- Супер-админ: политика `AdminOnly` пропускает `Admin` и `SuperAdmin`; роль супер-админа не может изменить никто (даже другой супер-админ), назначить её может только супер-админ, а бан/кик/сброс пароля супер-админа — только другой супер-админ. Первого супер-админа заводят в SQLite (`UPDATE Users SET Role = 100 WHERE Username = '...';`) и логинятся заново. `PartyHub` добавляет супер-админа в группу `admins`, `ModerationNotifier` шлёт ему push.
- Ключ подписи JWT резолвится по порядку «конфиг `Jwt:SigningKey` → файл `Jwt:KeysFile` (по умолчанию `App_Data/jwt.json`) → генерация» (`JwtSigningKeyStore`). Файл не удалять: после генерации нового ключа все выданные токены станут недействительными. В интеграционных тестах ключ задаётся env-переменной `Jwt__SigningKey`, чтобы файл не создавался.
- Бэкапы: `Modules/Backup/` — `GET /api/admin/backup` (свежий zip: `party.db` через SQLite Online Backup API, `vapid.json`, `jwt.json`, `uploads/`) и `GET /api/admin/backups` (список). `BackupBackgroundService` делает копию на старте и раз в `Backup:IntervalHours`, ротация — `Backup:KeepCount` (по умолчанию 5), каталог `Backup:Directory` (`App_Data/backups`), всё выключается `Backup:Enabled=false` (так сделано в интеграционных тестах).
- Действия админов пишутся в `AdminAuditLogs` (`AdminAuditService`, `GET /api/admin/audit`): начисления/списания, переименование, смена роли, бан/разбан, кик, сброс пароля. Вкладка «📜 Журнал» в SPA-админке.
- Логи: Serilog пишет в консоль и в файл `Serilog:LogFile` (`App_Data/logs/party-.log`, суточная ротация, 14 файлов). `/health` проверяет и БД, отдавая `{ status, database }` (503 при недоступной базе).
- Профиль и аватары: `Modules/Profile/` — `GET /api/profile`, `PATCH /api/profile` (только статус-эмодзи), `POST/DELETE /api/profile/avatar`, `GET /api/users/{id}/avatar` (авторизованно). Аватар лежит под `Files:UploadRoot` в папке `avatars/` (`IFileStorage.SaveAsync` с папкой; путь читается лениво при регистрации, чтобы учитывать конфиг хоста), в БД — `User.AvatarPath`/`StatusEmoji`/`ProfileUpdatedAt`. После изменений всем уходит `ProfileUpdated { userId, profileUpdatedAt }` — `Avatar.svelte` сбрасывает кэш по версии. Профиль открывается кликом по аватару в шапке; `ProfileModal` сжимает фото в квадрат 512 на клиенте. `profileUpdatedAt` отдаётся в админском списке игроков и лидерборде.
- Достижения: каталог в коде `Modules/Achievements/AchievementCatalog` (первый ответ, победитель квиза, фотограф, любимое фото, QR-охотник, душа компании, линия бинго, сотня), факт выдачи — `UserAchievement` (уникально «игрок+код»), награда — транзакция `WalletTransactionType.Achievement`. `AchievementService` (singleton) вызывается хуками из `EventService` (сабмит и финиш сессии), `PhotoEndpoints` (лайк и одобрение), `DareEndpoints` и `BingoService`; ошибки проверок логируются и не ломают основной сценарий. Игроку уходит `AchievementUnlocked` + push, каталог с моими отметками — `GET /api/achievements`, бейджи в профиле.
- Голосование за следующий ивент: `Modules/Polls/` — `Poll`/`PollOption`/`PollVote` (один голос на игрока, до закрытия можно передумать; в широковещательный DTO личный выбор не попадает). `GET /api/polls/current`, `POST /api/polls/{id}/vote`; админ создаёт (`POST /api/polls`, 2–8 активных определений, предыдущее голосование закрывается), закрывает (`POST .../close`) и запускает победителя (`POST .../start-winner` через `IEventService`). События `PollUpdated`/`PollClosed`; на большом экране режим `poll` (сам переключается на новое голосование), у игрока — карточка `PollCard` в `Party.svelte`, в админке — вкладка «🗳 Голосование».
- New event type requires: an `IEventHandler` in `src/PartyApp.Api/Modules/Events/Handlers/` (auto-registered via reflection; `EventType` must equal `EventDefinition.Type`), a seeded `EventDefinition` in `Program.cs`, and a UI branch in `web/src/lib/components/EventCard.svelte`. Для большого экрана и восстановления состояния игрока хендлеры могут переопределить `GetLiveDataAsync` (поле `live` в `GET /data`) и `GetPlayerDataAsync` (поле `player`). Фанты (`dare`) — особый случай: баллы начисляет админ после проверки (`/api/events/dare/pending`, `POST /api/events/dare/{id}/confirm`, игроку уходит `DareConfirmed`), назначения хранятся в `DareAssignments` (один фант на игрока за сессию). Бинго (`bingo`): игроки заранее отмечают клетки-предсказания (лимит `maxPredictions`, по умолчанию 3, поле «Максимум предсказаний» в редакторе ивента; уже подтверждённые клетки отмечаются сверх лимита, но баллов не приносят), админ подтверждает реальные события (`GET /api/events/bingo/{sessionId}`, `POST .../cells/{index}/confirm`, событие `BingoCellConfirmed`) и отклоняет неслучившиеся (`POST .../cells/{index}/reject`, событие `BingoCellRejected` — освобождает слоты предсказаний). Баллы за предсказание `pointsPerCell` получают все, кто отметил клетку заранее; бонус `lineBonus` за линию — один раз и только самому быстрому по времени последней отметки (`BingoLineAwards`, событие `BingoLineAwarded`), отклонения хранятся в `BingoCellRejections`. Большой экран получает сетку (`size`, `cells`, `confirmedCells`, `rejectedCells`) в live-данных (`GetLiveStateAsync`), после каждого решения админа и розыгрыша линии рассылается `EventLiveUpdated` (`BingoService`). Лототрон (`raffle`): игроки жмут «Участвовать» (обычные сабмиты), админ запускает розыгрыш `POST /api/events/raffle/{sessionId}/draw` — событие `RaffleDrawn` несёт участников и победителя, результат хранится в `RaffleDraws` (один раз на сессию); host-экран крутит колесо, победитель и уведомления показываются после анимации (`RAFFLE_SPIN_MS` на экране и телефонах). «Кто быстрее» (`reaction`) пишет время реакции в `PlayerSubmission.DurationMs` (через `SubmissionResult.DurationMs`), а `live` отдаёт `endsAtUtc` и отсортированный `results` (имя, мс, баллы) — экран показывает таблицу после закрытия окна нажатий. Note: `PartyApp.Domain.Abstractions.IEventHandler` is an unused empty stub — implement the `PartyApp.Api.Modules.Events.Handlers` one.
- Время окончания ивента: у `EventDefinition` есть `DurationMinutes` (поле «Длительность, мин» в редакторе; пусто — без автозавершения), сессия получает `EndsAt` при старте, и `EventClosingService` раз в 10 секунд завершает просроченные (как `AuctionClosingService` у лотов). `endsAt` отдаётся в `EventStarted`, `GET /api/events/available`, `GET /data` и в админском списке сессий; host-экран предпочитает его таймеру из конфига (`timeLimitSec`).
- QR-коды: `Modules/Qr/` — `GET /api/qr/tokens` (с полем `redeemedByName`), `POST /api/qr/tokens/generate`, `GET /api/qr/stats` (всего/активировано/осталось + счёт по игрокам). При активации рассылается `QrRedeemed` (экран обновляет статистику). В админке (`QrTab`) QR-картинки строятся на клиенте (`qrcode` npm): печать сеткой в отдельном окне (под каждым QR — текст кода и баллы) и PNG по одному. В QR зашита ссылка `/?qr=КОД`: `App.svelte` перехватывает параметр в `web/src/lib/qr.ts` и хранит его в `sessionStorage`, `Party.svelte` сам отправляет код в активный `qr_scan`-ивент, `EventCard` подставляет код вручную, если автоактивация не удалась.
- Фотоальбом и стенка пожеланий живут в `Modules/Photos/` и `Modules/Submissions/`; файлы фото лежат под `Files:UploadRoot` (`App_Data/uploads`), в БД только метаданные. Модерация управляется конфигом `Photos:RequireModeration` и `Wishes:RequireModeration` (по умолчанию оба true); админские вкладки «Фото»/«Пожелания» в SPA-админке. При загрузке игрок может добавить необязательную подпись (`PartyPhoto.Caption`, до 200 символов): она видна в ленте, админке и на большом экране, уходит в preview модерации, отдельно не модерируется и после отправки не редактируется. О новых материалах на модерации админам сообщает `Modules/Moderation/ModerationNotifier` — SignalR-событие `ModerationPending` в группу `admins` (хаб добавляет туда по роли при подключении) и push с тегом `moderation` (троттлинг 30 секунд на админа). За одобренное фото автору начисляются баллы (`RewardSettings.PhotoApprovedPoints`, по умолчанию 5, правится в админке) — ровно один раз на фото (флаг `PartyPhoto.RewardGranted`).
- Таймеры клиентов (реакция, тост, аукцион) считаются от серверного времени: `GET /api/time` + хелпер `web/src/lib/time.ts` (`serverNow()`), иначе телефоны и host-экран расходятся на секунды.
- Host-экран: `Modules/Screen/` (`GET/POST /api/screen/state`, `POST /api/screen/confetti`, `POST /api/screen/reactions`, `GET/PUT /api/screen/settings`) + singleton `ScreenService` в памяти; SPA-маршрут `/screen` (только админ) и вкладка «🖥 Экран» в админке. Режимы: `idle/leaderboard/event/photos/message/shop/lots/qr/spy/poll/rotation`; в `rotation` экран сам чередует фото → лидерборд → призы по таймаутам из настроек (`ScreenSettings`, правятся в админке). Состояние рассылается событием `ScreenUpdated`, конфетти — `ScreenConfetti`, стикеры и подписи от игроков — `ScreenReaction` (любой авторизованный, лимит `submit`). Экран сам переключается на свежий ивент по `EventStarted`, на лидерборд по `EventFinished` и на игру «Шпионаж» по `SpyGameStarted`/`SpyGameFinished` (режим `spy`: во время игры — игроки и обвинения без ролей и слова, после финиша — итог со шпионами и секретным словом); ручное переключение админом (`ScreenUpdated`) сбрасывает автопереход. В режиме `qr` и на экране активного `qr_scan`-ивента — статистика QR-охоты (всего/активировано/осталось + кто сколько нашёл), обновляется по `QrRedeemed`; в `lots` — активные ставки и блок «🏆 Выигранные лоты». Таймер ивента считается от `endsAt` сессии, иначе от `StartedAt` + `timeLimitSec` конфига. На экране ожидания показывается QR на `window.location.origin` («Сканируй, чтобы участвовать»), а рядом с «Режим игрока» в шапке админки — кнопка «📺 Режим TV» на `/screen`. «Живые» данные ивента отдаются в `GET /data` полем `live` (для `quick_checkin` — кто говорит тост) и обновляются событием `EventLiveUpdated`; хендлеры могут переопределить `IEventHandler.GetLiveDataAsync`.
- Магазин и аукцион: `Modules/Shop/` — товары/покупки и лоты. Списание баллов только через `IPointsAwardService.TrySpendAsync` (условный `UPDATE ... WHERE Balance >= amount`, без гонок). Лот создаётся черновиком (`Draft`) с длительностью в минутах, приём ставок открывает `POST /api/shop/lots/{id}/start` (`EndsAt = now + DurationMinutes`, событие `LotStarted`, плюс push и тост игрокам). Ставки открытые: `GET /lots` отдаёт лидера и сумму, каждый бид рассылает `BidPlaced`. Ставки удерживаются, при повышении списывается разница, проигравшим возвращаются при закрытии; просроченные лоты закрывает `AuctionClosingService` раз в 10 секунд, вручную — `close|cancel`. События `ShopUpdated`, `PurchaseUpdated`, `LotStarted`, `BidPlaced`, `LotFinished`, `LotCancelled` обновляют панели и экран без перезагрузки, а магазин перечитывается при возврате приложения из фона и после реконнекта SignalR — старт аукциона виден без перезагрузки страницы; на host-экране есть режим `lots` со ставками и таймером. Завершённые лоты с победителями отдаёт `GET /api/shop/lots/winners` (до 50, свежие сверху).
- Кошелёк: переводы между игроками `POST /api/wallet/transfer` (одна транзакция БД: условное списание + начисление, транзакции `TransferOut`/`TransferIn`, обоим `BalanceUpdated` и push; список получателей `GET /api/wallet/players`), админская история транзакций игрока `GET /api/admin/players/{playerId}/transactions` (форма `{ player, items, total }`, как у `/api/wallet/transactions`; вкладка «📊 Дашборд» → «📜 История»).
- `ToastService` and `SpyGameService` are singletons and keep game state in memory (lost on restart); event sessions/submissions are persisted in SQLite.
- Push-уведомления: `Modules/Push/` (`/api/push/subscribe`, `/unsubscribe`, `/test`, `/vapid-public-key`), отправка через NuGet `WebPush`. VAPID-ключи автогенерируются в `App_Data/vapid.json` (не удалять — иначе подписки станут невалидными), переопределяются конфигом `Push:*`. Обработчик `push`/`notificationclick` живёт в `web/public/push-sw.js` и подключается в сгенерированный SW через `workbox.importScripts`. В Vite dev service worker выключен, поэтому PWA и push проверяются только на собранном приложении (`npm run build` + API). На iOS push работает лишь в приложении, добавленном на экран «Домой» (iOS 16.4+, Safari), и только по HTTPS. Баллы начисляются через `Modules/Wallet/PointsAwardService` — там же рассылка `BalanceUpdated` и push.
- Обновления PWA: `registerType: 'autoUpdate'` + `injectRegister: false`, регистрация своя (`web/src/lib/pwa.ts`): проверка обновлений сразу при старте и раз в минуту, страховочный reload по `controllerchange` (если Workbox не перезагрузил). HTML не прекешируется (`globPatterns` без `html`, `navigateFallback: null`), навигации идут через `NetworkFirst` (`pages`) — обычная перезагрузка всегда отдаёт свежую оболочку, даже пока SW не обновился. HTML-файлы отдаются с `Cache-Control: no-cache`. В шапке админки — штамп сборки и кнопка «↻ Обновить» (`forceRefreshApp`: снимает SW, чистит кэши, перезагружает) для застрявших клиентов, особенно iOS.
- Хостинг: `deploy/Caddyfile` + `deploy/README.md` — Caddy терминирует HTTPS и проксирует на `localhost:5000`. Корень `/` отдаёт SPA (`MapFallbackToFile`); API-документация осталась на `/swagger`.
- Claims are not remapped (`MapInboundClaims = false`): `sub`, `name`, `role`, `stamp`. `Clients.User(playerId)` works because `SubClaimUserIdProvider` uses `sub`. `stamp` сверяется с `User.SecurityStamp` и `IsActive` на каждом запросе (`OnTokenValidated`), поэтому отзыв сессий работает без списка токенов. На фронте 401 от `api()` и истёкший токен при SignalR-подключении/реконнекте (`isTokenExpired` в `api.ts`) чистят сессию и перезагружают страницу — долго открытые вкладки и ТВ не залипают в цикле 401, а возвращаются на экран входа.
- CORS allows only `http://localhost:5173`; SignalR takes the JWT from the `access_token` query string for `/hubs`.
- Rate limiting включается конфигом `RateLimiting:*` (`Enabled`, `AuthPermitLimit`, `SubmitTokenLimit` и т.д.) и читается на каждый запрос. В интеграционных тестах выключен настройкой в `PartyAppFactory`; тесты самих лимитов поднимают отдельную фабрику через `ConfigureOverrides`.

## Conventions

- `.editorconfig` is authoritative: 4 spaces, file-scoped namespaces, braces on new lines, `var` avoided; private fields `_camelCase`, private static fields `s_camelCase`, constants PascalCase; `.cs` files get no final newline.
- Keep feature code under `Modules/<Feature>/` as static `Map*Endpoints` extension classes; register new maps in `Program.cs`.
- Singleton handlers/services must resolve `AppDbContext` via `IServiceScopeFactory` (as the existing handlers do), never inject the scoped context.
